# 运行手册

## 启动

```bash
docker compose up -d --build
open http://127.0.0.1:18207/
```

首次启动库是空的，页面上点「运行样例」或执行：

```bash
curl -s -X POST http://127.0.0.1:18207/api/import \
  -H 'Content-Type: application/json' -d '{"dataset":"dirty"}'
```

## 数据集

| 名称 | 用途 |
|---|---|
| `dirty` | 脏样例，含 9 类问题，演示隔离与原因码 |
| `clean` | 干净样例，验证同一条代码路径 |
| `header_only` | 仅表头 |
| `blank` | 全空行 |
| `empty` | 0 字节文件 |
| `settlement/` | 媒体月结批次：`2026-09.csv`、`2026-10.csv`（已核销）、`2026-11-pending.csv`（待确认） |
| `rebate_contract.json` | 返点合同：各渠道累计花费阶梯与费率 |

## 返点结算流程

1. 运行一次导入（`POST /api/import`），确认触点与成交额。
2. 「返点结算」页点「导入样例结算」，或 `POST /api/settlements/samples`；
   等价于逐个导入 `sample_data/settlement/*.csv`。
3. 核对：渠道累计已结算花费、当前档位与费率、距下一档差额、已核销 vs 待确认返点。
4. 「预算与批次」页选成本口径：
   - `auto`：六渠道都有已确认结算时用「返点后成本」，否则退回观察花费；
   - `settled`：只用已核销返点后成本，缺证据则 409 且不写新版本；
   - `observed`：只看本轮导入的花费。
5. 提交新版本后，页面上能同时看到「花费 / 上版预算 / 本版预算 / 预算增减 / 返点后成本 / 基础与边际 ROI」。

## 重跑

同一份输入重复导入会命中同一个 `run_id`，接口返回 `repeat=true`，行数不变。
换数据集或改规则版本才会产生新的 `run_id`。

结算批次同理：同一份月结文件重复导入返回 `repeat=true`，返点不会重复累加。
改了账期、渠道、花费或返点内容再导入，才会得到新的 `batch_id`；同渠道同账期若已有正式结算，整批 409。

## 重置

```bash
docker compose down -v          # 删除 SQLite 命名卷
docker compose up -d --build
```

## 日志

页面「作业总览」右侧是运行日志尾，每行带时间戳与级别，可暂停滚动；
接口为 `GET /api/runs/{run_id}/log?after=<seq>`。

## 排查顺序

1. 「触点与订单」看状态与原因码，确认丢弃的是哪一行、物理行号多少。
2. 「隔离区」看原因码分布，导出 CSV 交给投放同学对照原始导出。
3. 「归因结果」看五个模型合计是否都等于订单成交额。
4. 「置信区间」看份额区间与结论：半宽过大或首位不稳说明订单簇太少，补数据再算。
5. 「返点结算」看档位与返点：累计花费没跨档就看合同门槛，媒体返点与合同不一致会标出来。
6. 「预算与批次」看成本口径：显示「观察」说明还没有已核销证据，别把待确认返点当到账。
7. 「导出」看运行清单的 `recomputed_run_id` 是否与 `run_id` 一致。
